# embedded-lab 学习笔记

> [!note] 基础知识深入层
> 当前 P0 主课程背后新增了一层可跳转的基础知识网络：
>
> [[10_基础知识体系/00_基础知识总地图]]
>
> 学习时仍以课程主线为准；遇到陌生概念再点进去深挖，理解后返回原页面。

这套 Obsidian 笔记服务于 `embedded_lab` 实验仓库。

它不是源码仓库的复制品，也不是把参考手册重新抄一遍。它承担三个任务：

1. **记录学习顺序**：我为什么先学这个，再学下一个。
2. **保存机制理解**：一个现象背后的因果链到底是什么。
3. **保存验证证据**：我用什么源码、ELF、调试器或仪器证明自己的理解。

实际源码、构建产物和硬件实验仍然发生在 `embedded_lab` 工程中。本知识库只保存**理解、推导、验证方法和实验结论**。

## 3. 每篇课程笔记统一回答六个问题

以后每篇笔记都尽量遵循同一种阅读方式。

### ① 这节课解决什么问题？

先知道为什么学，否则很容易陷入文件细节。

### ② 它对应仓库中的什么东西？

知识必须能落回真实工程：

```text
概念
  ↓
文件 / CMake target / ELF symbol / 寄存器
  ↓
真实行为
```

### ③ 因果链是什么？

不要只记定义，要能讲清：

```text
A 为什么导致 B
B 又为什么导致 C
```

### ④ 怎样验证？

优先级通常是：

```text
源码
  ↓
详细构建命令
  ↓
ELF / symbol / section
  ↓
调试器
  ↓
真实硬件与仪器
```

### ⑤ 最容易误解什么？

把自己曾经踩过的坑留下，比只记“正确答案”更有价值。

### ⑥ 闭卷时能不能重新讲出来？

读完一篇后，关掉笔记，至少能回答页面末尾的“离开本页前”。

## 4. 本课程的学习方法

整个 `embedded_lab` 尽量遵循下面的循环：

```text
提出问题
   ↓
查官方资料
   ↓
形成预测
   ↓
写最小代码 / 配置
   ↓
构建
   ↓
观察 ELF / 调试器 / 硬件
   ↓
故障注入
   ↓
解释现象
   ↓
形成结论
```

核心不是“做出效果”，而是：

> **我能否提前预测结果，并用证据解释结果为什么如此。**

例如：

- LED 亮了，不等于理解 GPIO。
- ELF 生成了，不等于程序已经正确运行。
- `main()` 执行了，不等于所有 startup 行为都已经验证。
- 一个寄存器读回了预期值，也不一定证明引脚物理电平正确。

## 5. 关于官方资料与自己的笔记

资料分三层看：

```text
官方资料
   ↓
回答“事实是什么”

工程源码 / 构建产物
   ↓
回答“当前工程实际上选择了什么”

自己的 Obsidian 笔记
   ↓
回答“我怎样理解并验证它”
```

因此不要把自己的笔记当成新的“官方手册”。

当笔记和源码、RM、Datasheet 冲突时，应回到一手资料核对并修正笔记。

## 6. 关于代码片段

笔记中的代码分两类。

### 教学示意代码

只为了解释机制：

```c
volatile int x = 10;
```

不保证可以直接复制进工程。

### 当前工程代码

如果笔记明确说“来自当前仓库”，则应该能在 `embedded_lab` 中找到对应文件。

为防止未来仓库演进导致笔记失真，重要结论最好同时记录：

- 主仓库 commit
- STM32CubeF4 submodule commit
- 构建命令
- ELF 路径
- 必要时保存关键输出

## 7. P0 的最终学习目标

P0 完成后，不要求背下每一个 CMake 语法或 linker script 写法。

真正要能闭卷讲清的是：

```text
main.c
  ↓
CMake 选择构建对象
  ↓
ARM GNU 交叉编译
  ↓
.o
  ↓
Linker Script 决定最终地址
  ↓
ELF
  ↓
烧录到 Flash
  ↓
Cortex-M 复位读取向量表
  ↓
Reset_Handler
  ↓
SystemInit
  ↓
.data 初始化
  ↓
.bss 清零
  ↓
C/C++ runtime 初始化
  ↓
main()
```

并且知道：

> 哪一段结论应该去哪个文件或工具里找证据。

从 [[00_课程索引]] 开始。
