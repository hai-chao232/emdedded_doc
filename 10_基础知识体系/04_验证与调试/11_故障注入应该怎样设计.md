# 故障注入应该怎样设计？

## 一句话先说清

故障注入不是“随便改坏代码看看”。好的故障实验先写预测，只改变一个关键条件，再观察证据是否按因果链发生变化。

---

# 1. 四步模板

```text
① 正常机制是什么？
② 我要故意破坏哪一个条件？
③ 破坏后我预测会发生什么？
④ 用什么证据判断预测对不对？
```

---

# 2. P0 例子：去掉 `.data` copy

正常：

```text
Flash initial image
→ startup copy
→ SRAM counter = 10
```

故障：

```text
跳过 copy
```

预测：

```text
counter 不再保证 10
```

证据：

```text
ELF 仍然有 initial image
但 main 的 RAM 状态不再可靠
```

---

# 3. 001 GPIO 例子：不打开 GPIOB clock

正常链：

```text
RCC enable
→ GPIO register interface active
→ configure MODER
→ output
```

故障：

```text
故意不 enable GPIOB clock
```

先预测：

```text
寄存器写入/外设行为会如何？
LED/引脚电平会怎样？
```

再查 RM 并实测。

---

# 4. 一次只破坏一个变量

如果同时：

```text
关 RCC
改错引脚
改错 MODER
```

最后 LED 不亮毫无诊断价值。

---

# 5. 要有恢复点

故障实验前：

```text
Git clean state
commit / diff
```

实验后恢复。

不要让“教学破坏”混进主线工程。

---

# 6. 记录预期与实测差异

最有价值的往往不是“预测正确”，而是：

```text
为什么我的预测错了？
我漏了哪一层机制？
```

这会自然生成新的 Obsidian 知识链接。
