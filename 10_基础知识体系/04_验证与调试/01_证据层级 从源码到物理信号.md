# 证据层级：从源码到物理信号

## 一句话先说清

“代码里写了”是最弱的一层证据。要验证一个嵌入式结论，需要逐层区分：配置意图、构建结果、CPU 运行状态、外设状态和真实物理信号。

---

# 1. 五层证据

## 第 1 层：Source

```text
我在 CMake 里写了 -DSTM32F446xx
我在代码里写了 GPIOB->MODER
```

只证明：

> 你有这个意图。

---

## 第 2 层：Build Command / ELF

```text
详细 compile command
link command
ELF section
symbol
disassembly
```

证明：

> 工具链实际生成了什么。

---

## 第 3 层：CPU Runtime

Debugger 看：

```text
PC
SP
register
RAM
peripheral register
```

证明：

> 真实 CPU 当前执行/保存的状态。

---

## 第 4 层：Peripheral State

例如：

```text
GPIOB MODER 确实为 output
ODR/BSRR 操作后 IDR/ODR 状态
RCC enable bit
```

证明外设配置层。

---

## 第 5 层：Physical Signal

例如：

```text
PB0 = 3.3 V
逻辑分析仪波形
LED 状态
示波器频率
```

这才证明外部世界真正发生了结果。

---

# 2. 一个 GPIO 例子

命题：

> PB0 被配置成输出高电平。

证据链：

```text
源码有配置
↓
反汇编有写寄存器指令
↓
Debugger 读 MODER/ODR 符合预期
↓
万用表测 PB0 接近高电平
```

每一层都比上一层更接近结论。

---

# 3. 一个 Startup 例子

命题：

> `.data` 初值已被复制到 SRAM。

源码看到 copy loop：

```text
只说明程序里有这个逻辑
```

ELF：

```text
说明 source/destination 地址安排合理
```

Debugger 在 main：

```text
counter == 10
```

更强。

在 Reset_Handler copy 前后观察：

---

# 4. 反例：寄存器正确但 LED 不亮

这完全可能。

原因：

```text
原理图理解错
LED active-low
跳线/焊桥状态不同
引脚复用冲突
硬件损坏
```

所以：

> 软件寄存器证据不能替代物理验证。
