# C 变量的存储期、作用域与链接属性

## 一句话先说清

“变量放在哪里”“名字在哪能看见”“程序运行多久它存在”是三个不同问题。初学时把它们混在一起，会直接导致 `.data/.bss/stack/static/extern` 全部混乱。

---

## 1. 三个问题先分开

### Scope 作用域

源代码里：

> 这个名字在哪一段代码可见？

### Storage Duration 存储期

运行时：

> 这个对象从什么时候存在到什么时候？

### Linkage 链接属性

跨翻译单元：

> 这个名字能不能和别的 `.c` 文件里的同名声明关联到同一个实体？

三者相关，但不是一回事。

---

## 2. 自动存储期

典型：

```c
void f(void)
{
    int x = 1;
}
```

`x` 通常是 automatic storage duration。

概念上：

```text
进入函数
→ x 的生命周期开始

离开函数
→ x 的生命周期结束
```

实际是否真的放栈，由编译器优化决定。

它可能：

- 在寄存器里；
- 在栈里；
- 被完全优化掉。

所以不要死记：

> “局部变量一定在栈”。

---

## 3. 静态存储期

例如：

```c
int global;
static int file_state;
```

以及：

```c
void f(void)
{
    static int count;
}
```

这些对象都有 static storage duration：

```text
程序开始时存在
直到程序结束
```

在裸机里，通常就是整个程序运行期间。

它们常进入：

```text
.data
.bss
.rodata（取决于 const / 使用方式等）
```

---

## 4. 全局变量与 static 局部变量为什么都可能在 `.bss`？

因为 section 分类主要关心：

```text
数据属性与初始化需求
```

而不是：

```text
源代码作用域是否全局
```

例如：

```c
int a;
```

和：

```c
void f(void)
{
    static int b;
}
```

二者都可能进入 `.bss`。

但：

```text
a 的名字可能具有外部 linkage
b 只在函数作用域内可见
```

这就是为什么作用域和存储位置不能混为一谈。

---

## 5. `extern` 不是“把变量放到外部内存”

```c
extern int x;
```

表示：

> 这里声明 x，但定义通常在别的翻译单元。

它与 SRAM/Flash 的“外部”完全不是一个意思。

---

## 6. 文件作用域 `static`

```c
static int state;
```

在文件作用域时，`static` 常使名字具有 internal linkage：

> 只在当前 translation unit 内部链接可见。

这对避免跨文件 symbol 冲突非常重要。

---

## 7. 函数内部 `static`

```c
void f(void)
{
    static int count;
}
```

这里 `static` 主要改变的是：

> storage duration

`count` 不会每次函数退出就失去状态。

它仍然只有函数内作用域。

---

## 8. 为什么这和 startup 有直接关系？

静态存储期对象必须在 `main()` 前符合 C 语言初始化要求：

```text
非零初值
→ .data
→ startup copy

零/无显式初值
→ .bss
→ startup clear
```

所以 startup 并不是 STM32 的“额外习惯”，而是在建立 C 语言期望的程序初始状态。

---

## 9. 一个表先记住

| 示例 | 常见存储期 | 常见运行位置 |
|---|---|---|
| `int g = 1;` | static | `.data` / SRAM |
| `int g;` | static | `.bss` / SRAM |
| `const int c = 1;` | static | 常见 `.rodata` / Flash |
| 函数局部 `int x;` | automatic | 寄存器/stack/优化 |
| 函数局部 `static int x;` | static | `.bss/.data` / SRAM |

“常见”不等于语言标准强制具体 section。
