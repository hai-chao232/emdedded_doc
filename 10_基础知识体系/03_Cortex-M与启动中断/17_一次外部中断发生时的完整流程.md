# 一次外部中断发生时的完整流程

这页先建立全景，003/004 实验时再把每个寄存器补进去。

---

# 1. 以 GPIO 边沿为例

```text
外部电平变化
    ↓
GPIO / SYSCFG / EXTI 配置使该引脚成为 EXTI source
    ↓
EXTI 检测到配置的 edge
    ↓
EXTI pending/request
    ↓
IRQ line 到 Cortex-M NVIC
    ↓
NVIC 检查 enable / priority / masking
    ↓
CPU 接受 exception
    ↓
硬件自动保存基本现场到 stack
    ↓
根据 exception number 查询 Vector Table
    ↓
取得 EXTIx_IRQHandler entry
    ↓
进入用户 handler
    ↓
软件处理事件并清外设 pending 条件
    ↓
exception return
    ↓
硬件恢复原现场
    ↓
继续被打断代码
```

---

# 2. 哪些属于 STM32 外设？

```text
GPIO
SYSCFG
EXTI
```

查 STM32 RM。

---

# 3. 哪些属于 Cortex-M？

```text
NVIC
exception entry
automatic stacking
vector lookup
exception return
```

查 Cortex-M / CMSIS。

---

# 4. Startup 在这里扮演什么角色？

Startup 在构建时提供：

```text
向量表中的 EXTI handler symbol entry
默认 weak handler
```

正常运行时不会每次中断都重新执行 Reset_Handler。

---

# 5. Linker 在这里扮演什么角色？

Linker 已提前确定：

```text
vector table address
handler function address
symbol resolution
```

中断发生时 linker 已经不在场。

---

# 6. 为什么 handler 必须清 pending？

很多外设中断条件如果不清除：

```text
handler 返回
→ 请求仍存在
→ 立即再次进入
```

具体清除规则由外设定义。

这不是 NVIC 自动替所有外设完成的。

---

# 7. 这条链为什么重要？

遇到“中断不进”时你就可以分层查：

```text
物理信号有吗？
EXTI 检测了吗？
pending 了吗？
NVIC enable 了吗？
mask/priority 允许吗？
vector entry 对吗？
handler 名字对吗？
handler 进去后是否清 pending？
```

而不是只反复改一行 `NVIC_EnableIRQ()`。
