## 0. 先确认对象

```text
embedded_lab/platform/stm32f446ze/linker/STM32F446ZE.ld
```

它由 STM32CubeIDE 自动生成（文件头写明 `Auto-generated by STM32CubeIDE`），你的 `platform/stm32f446ze/CMakeLists.txt` 用这一行把它交给链接器：

```cmake

    platform_stm32f446ze
    INTERFACE
    -T${STM32F446ZE_LINKER_SCRIPT}
```

## 1. 全文结构地图

读任何链接脚本前，先找这五块：

```text
① ENTRY(...)          → 谁是入口（对我们只是个声明）
② MEMORY { }          → 芯片有哪些地址区域，多大
③ 顶层赋值             → _estack、_Min_Heap_Size、_Min_Stack_Size
④ SECTIONS { }        → 每个段放哪、怎么排、边界符号是谁
⑤ /DISCARD/ 及其他     → 清理和元数据
```

对应的行号（以当前文件为准）：

```text
36          ENTRY(Reset_Handler)
39          _estack = ORIGIN(RAM) + LENGTH(RAM);
41-42       _Min_Heap_Size / _Min_Stack_Size
45-49       MEMORY { }
52-187      SECTIONS { }
179-184     /DISCARD/
186         .ARM.attributes
```

## 2. `ENTRY(Reset_Handler)`（第 36 行）

```ld
ENTRY(Reset_Handler)
```

**它不是"让 CPU 从 Reset_Handler 启动"的原因。**

它只做一件事：把这个符号名写进 ELF Header 的 `e_entry` 字段。

```text
ENTRY(Reset_Handler)
    ↓
ELF Header 的 e_entry = Reset_Handler 的地址
```

而 Cortex-M 上电时**不读 e_entry**，它读的是向量表第 1 项。

所以这两件事必须分开：

```text
ENTRY() 声明的       → ELF 文件格式层面的入口信息
向量表第 1 项        → Cortex-M 硬件实际使用的复位入口
```

> [!important] 验证方法
> ```bash
> arm-none-eabi-readelf -h build/experiments/001_gpio_output/exp001_gpio_output.elf | grep Entry
> ```
> 你会看到 `Entry point address: 0x8000xxx`。
> 这个值和 `nm` 里 `Reset_Handler` 的地址应该**基本一致**——但这只是巧合式的吻合，不是因果。
> 把 `ENTRY(Reset_Handler)` 改成别的函数，`e_entry` 会跟着变，**芯片复位行为却完全不变**。

## 3. `_estack`（第 39 行）

```ld
_estack = ORIGIN(RAM) + LENGTH(RAM);   /* end of "RAM" Ram type memory */
```

代入你的 `MEMORY` 定义：

```text
ORIGIN(RAM) = 0x20000000
LENGTH(RAM) = 128K = 0x20000
_estack     = 0x20020000
```

### 为什么是"越过末尾"的地址？

因为栈**向下增长**，且是**先减后写**：

```text
第一次压栈：
  SP = 0x20020000 - 4 = 0x2001FFFC
  然后写 [0x2001FFFC]
```

所以 `0x20020000` 这个地址**本身从来没有被访问过**。它只是"栈的起点"。

这也解释了为什么它落在 RAM 范围之外（RAM 最后一个有效字节是 `0x2001FFFF`）却完全合法。

### 它在启动链里的位置

```text
向量表第 0 项 = _estack
        ↓
CPU 复位时把它装进 MSP
        ↓
之后所有 C 函数的栈帧从这里往下走
```

> [!important] 验证方法
> ```bash
> arm-none-eabi-objdump -s -j .isr_vector build/.../exp001_gpio_output.elf | head -5
> ```
> 第一行 4 个字节按小端读出来，应该正好是 `00 00 02 20` → `0x20020000`。

## 4. `_Min_Heap_Size` 和 `_Min_Stack_Size`（第 41-42 行）

```ld
_Min_Heap_Size  = 0x200;   /* 512 B  */
_Min_Stack_Size = 0x400;   /* 1024 B */
```

> [!danger] 这两个是 P0 阶段最容易被误解的地方
> 它们**不是**"堆的大小"和"栈的大小"。
>
> 它们是**链接器为了保证 RAM 不会溢出而做的预留登记**。
> 真正的栈大小是你**运行时实际压了多少**（上限由 `_estack` 往下、撞到哪里决定）。
> 真正的堆大小在裸机 P0 阶段是 **0**——因为 `malloc` 根本还没人调用。

这两个值后面在第 11 节会再出现一次，并且**直接决定 `size.bss` 的读数**。

## 5. `MEMORY { }`（第 45-49 行）

```ld
MEMORY
{
  RAM    (xrw)    : ORIGIN = 0x20000000,   LENGTH = 128K
  ROM    (rx)     : ORIGIN = 0x08000000,   LENGTH = 512K
}
```

### 这四行在说什么

| 名称 | 地址起点 | 长度 | 权限 | 对应物理 |
|---|---|---|---|---|
| `RAM` | `0x20000000` | 128 KB | `xrw` 执行/读/写 | SRAM1+SRAM2 连续区 |
| `ROM` | `0x08000000` | 512 KB | `rx` 读/执行 | 主 Flash |

> [!note] 这里叫 `ROM` 不叫 `FLASH`
> 你在其他教程里会看到 `FLASH (rx) : ORIGIN = 0x08000000`。
> 名字是**任意的**，只是个标签。真正有意义的是**后面的地址和权限**。
> 读别人的脚本时不要因为名字不同就以为语义不同。

### 权限字母的含义

```text
r → read     可读
w → write    可写
x → execute  可执行
```

它们**不会**真的配置 MPU，只是告诉链接器"这个区域能不能放需要写的内容"。
把 `.data` 放到 `(rx)` 的区域，链接器会报错——这就是它的作用。

> [!important] 验证方法
> `0x08000000 + 512K = 0x08080000`，`0x20000000 + 128K = 0x20020000`。
> 用 `arm-none-eabi-size` 看你的 ELF，Flash 用量必须 < 512K，否则链接阶段就会报 `region ROM overflowed`。

## 6. `.isr_vector`（第 55-60 行）

```ld
.isr_vector :
{
  . = ALIGN(4);
  KEEP(*(.isr_vector))
  . = ALIGN(4);
} >ROM
```

三件事：

```text
. = ALIGN(4);        → 当前位置对齐到 4 字节
KEEP(*(.isr_vector)) → 收集所有 .o 里的 .isr_vector 段，且禁止 gc-sections 回收
>ROM                 → 安排到 ROM 区域
```

### 为什么必须放第一个

它不是"约定"，是**硬约束**：

```text
Cortex-M 复位时从 0x08000000（经 boot alias 后）读第 0 项 = 初始 MSP
                    从 0x08000004 读第 1 项 = Reset_Handler
```

如果 `.isr_vector` 不是 ROM 里第一个段，CPU 读到的就是别的数据。

### 为什么需要 `KEEP`

你的链接选项里有：

```text
-Wl,--gc-sections
```

开启后，链接器会回收"没有任何代码引用"的段。

向量表**恰恰没有代码引用它**——引用它的是**硬件**。链接器看不见硬件，所以必须手工 `KEEP`。

> [!important] 验证方法
> ```bash
> arm-none-eabi-objdump -h build/.../exp001_gpio_output.elf | head -12
> ```
> 确认 `.isr_vector` 的 VMA 是 `0x08000000`，且它是输出里**第一个**有内容的段。

## 7. `.text` 和 `.rodata`（第 63-86 行）

```ld
.text :
{
  . = ALIGN(4);
  *(.text)           /* .text sections (code) */
  *(.text*)          /* .text* sections (code) */
  *(.glue_7)         /* glue arm to thumb code */
  *(.glue_7t)        /* glue thumb to arm code */
  *(.eh_frame)

  KEEP (*(.init))
  KEEP (*(.fini))

  . = ALIGN(4);
  _etext = .;        /* define a global symbols at end of code */
} >ROM
```

### 输入段的通配规则

```text
*(.text)    → 精确匹配叫 .text 的输入段
*(.text*)   → 匹配 .text、.text.foo、.text_1 等所有以 .text 开头的
```

你的编译选项有：

```text
-ffunction-sections
```

它让**每个函数**单独成为一个输入段，名字类似 `.text.main`、`.text.Reset_Handler`。
所以 `*(.text*)` 这条通配是**必须的**——只有 `*(.text)` 会丢掉所有函数。

> [!note] 这正是 `-ffunction-sections` 和 `--gc-sections` 配合的前提
> 函数被拆成独立段，链接器才能**逐个**判断"这个函数有没有人用"，没有就删。
> 如果所有函数挤在一个 `.text` 里，就只能整块保留或整块删除。

### `_etext` 是什么

```text
_etext = .;   → 记录代码段结束的位置
```

P0 用不到它，但你要知道它**不是**"Flash 里内容的结束"。
后面还有 `.rodata`、`.ARM.exidx`、`.data` 的加载镜像等。

## 8. 那一堆你可能没见过的段（第 88-131 行）

```ld
.ARM.extab  (READONLY) : { ... } >ROM
.ARM        (READONLY) : { ... } >ROM
.preinit_array (READONLY) : { ... } >ROM
.init_array    (READONLY) : { ... } >ROM
.fini_array    (READONLY) : { ... } >ROM
```

> [!tip] P0 阶段怎么对待它们
> **先记住"它们存在、都在 ROM、现在都可忽略"就够了。**

但要解释清楚为什么会有它们：

### `.ARM.extab` / `.ARM`（`.ARM.exidx`）

ARM EABI 的**异常处理索引表**。

C++ 异常、`backtrace()` 之类需要它。裸机 C 程序用不到，但编译器**默认会生成**。

```text
__exidx_start = .;
*(.ARM.exidx*)
__exidx_end = .;
```

这两个符号是给 C++ 运行时库查表用的。

你在 `objdump -h` 输出里**一定会看到 `.ARM.exidx`**，不要为此困惑——它跟向量表毫无关系。

### `.preinit_array` / `.init_array` / `.fini_array`

**函数指针数组**。

```text
.init_array → 一组"启动时要调用的函数"的地址
```

C++ 全局对象构造函数、`__attribute__((constructor))` 都注册在这里。

调用它的是 `__libc_init_array`：

```text
Reset_Handler
    ↓ bl
__libc_init_array    ← 一个 C 函数，可以被 bl
    ↓ 遍历
.init_array          ← 一张数据表，不能被 bl
    ↓ 逐个调用
你的构造函数们
```

> [!warning] 一个常见误读
> `.init_array` 是**数据**（函数指针表），不是代码。
> `bl .init_array` 是非法的。能 `bl` 的只有 `__libc_init_array`。

注意 `PROVIDE_HIDDEN`：它定义符号，但**只在被引用时才真正产生**，且不导出到符号表外部。

还有 `SORT(.init_array.*)`：按名字排序。因为构造函数可能有优先级（`.init_array.00101` 这种编号），**顺序必须确定**。

## 9. `.data`：本页最关键的一段（第 133-149 行）

```ld
/* Used by the startup to initialize data */
_sidata = LOADADDR(.data);

/* Initialized data sections into "RAM" Ram type memory */
.data :
{
  . = ALIGN(4);
  _sdata = .;        /* create a global symbol at data start */
  *(.data)           /* .data sections */
  *(.data*)          /* .data* sections */
  *(.RamFunc)        /* .RamFunc sections */
  *(.RamFunc*)       /* .RamFunc* sections */

  . = ALIGN(4);
  _edata = .;        /* define a global symbol at data end */

} >RAM AT> ROM
```

### `>RAM AT> ROM` 是整份脚本里最重要的一行

```text
>RAM      → VMA（运行地址）在 RAM
AT> ROM   → LMA（加载地址）在 ROM
```

这就是"一个变量同时占两个地址"的**直接来源**。

```text
        ROM (Flash)                    RAM
   ┌──────────────────┐          ┌──────────────────┐
   │ .data 初始化镜像  │  copy→   │ .data 运行实体    │
   │ _sidata = 0x08000334        │ _sdata = 0x20000000
   └──────────────────┘          └──────────────────┘
          LMA                            VMA
```

### `_sidata` 为什么写在 `.data` **外面**

```ld
_sidata = LOADADDR(.data);   ← 在 SECTIONS 里，但在 .data 块之外
```

`LOADADDR()` 取的是 `.data` 的**加载地址**（LMA）。

**所以 `_sidata` 只有一个，没有 `_eidata`。**

源区长度靠 `_edata - _sdata` 算出来——因为两个区长度必然相等。

```text
源范围：[_sidata, _sidata + (_edata - _sdata) )
目标范围：[_sdata,  _edata )
```

这解释了为什么你的 `nm` 输出里找不到 `_eidata`——**它本来就不该存在**。

### `_sdata` / `_edata` 是"变量"吗

不是。

```ld
_sdata = .;
```

不是分配 RAM，是**给"当前位置"起了个名字**。

它们在符号表里是**绝对值符号**，类型字母是 `A` 或 `D`，但**不占任何存储**。

> [!important] 验证方法
> ```bash
> arm-none-eabi-objdump -h build/.../exp001_gpio_output.elf | grep -A1 "\.data"
> ```
> 注意 `.data` 那行会有**两个地址列**：`VMA` 和 `LMA`。
> 当前最小程序里 `data = 0`，所以这两个值可能都不显眼；
> 一旦你加了 `uint32_t counter = 10;`，VMA 会落在 `0x20000000`，LMA 会落在 Flash 里。

## 10. `.bss`（第 151-165 行）

```ld
. = ALIGN(4);
.bss :
{
  /* This is used by the startup in order to initialize the .bss section */
  _sbss = .;         /* define a global symbol at bss start */
  __bss_start__ = _sbss;
  *(.bss)
  *(.bss*)
  *(COMMON)

  . = ALIGN(4);
  _ebss = .;         /* define a global symbol at bss end */
  __bss_end__ = _ebss;
} >RAM
```

### 注意：只有 `>RAM`，**没有** `AT> ROM`

```text
.data : >RAM AT> ROM    ← 两份（Flash 存初值，RAM 运行）
.bss  : >RAM            ← 只有一份（RAM 运行，没有 Flash 镜像）
```

这一个字的差别，就是 `.bss` 不占 Flash 的**全部原因**。

### 为什么不需要 Flash 镜像

因为初值是**全零**，而"全零"不需要存——启动时写一遍就行。

```text
如果 Flash 存 4096 个零：
    浪费 4096 B Flash

现在的做法：
    Flash 存 0 B
    Reset_Handler 遍历 [_sbss, _ebss) 写 0
```

### `*(COMMON)` 是什么

C 里的** tentative definition**：

```c
int x;          // 暂定定义
int x = 5;      // 真正的定义
```

多个 `.c` 文件都写 `int x;` 时，编译器先把它们放 `COMMON` 段，由链接器合并成一份。
这是 C 语言历史遗留行为，现代编译器加 `-fno-common` 后会直接放 `.bss`。

### `__bss_start__` / `__bss_end__`

这是**同一批地址的别名**：

```text
_sbss         == __bss_start__
_ebss         == __bss_end__
```

ST 生成的 startup 汇编里用的是 `__bss_start__` / `__bss_end__`，而链接脚本里 `_sbss` / `_ebss` 是另一种命名习惯。

**你在 `nm` 里会同时看到两套符号名，地址完全相同。** 不要以为是两组不同的区域。

## 11. `._user_heap_stack`：`1568` 的答案（第 167-176 行）

```ld
/* User_heap_stack section, used to check that there is enough "RAM" Ram  type memory left */
._user_heap_stack :
{
  . = ALIGN(8);
  PROVIDE ( end = . );
  PROVIDE ( _end = . );
  . = . + _Min_Heap_Size;
  . = . + _Min_Stack_Size;
  . = ALIGN(8);
} >RAM
```

> [!success] 这就是那个悬案的答案
> [[01_P0_仓库与构建基线/07_最小 Executable 与 ELF 体检]] 里问过：
> **为什么 `size.bss = 1568`，而 `_ebss - _sbss` 只有 28 B？**
>
> 答案就在这里：**`._user_heap_stack` 也被 `size` 算进 `bss` 列。**

### 逐行拆开

```ld
. = ALIGN(8);            ← 当前位置对齐到 8 字节
PROVIDE ( end = . );     ← 定义 end 符号 = 这里（malloc 的起点）
PROVIDE ( _end = . );    ← 同上，另一套命名
. = . + _Min_Heap_Size;  ← 位置指针 +512
. = . + _Min_Stack_Size; ← 位置指针再 +1024
. = ALIGN(8);            ← 末尾再对齐
```

### 关键：它**不产生任何字节**

注意这一段里**没有 `*(...)`**。

其他段都是"收集输入段放进来"，这一段只是**把位置计数器往前推**。

```text
. = . + 512;    ← 不是"写入 512 个字节"
                ← 而是"声明接下来的 512 字节被预留了"
```

所以：

```text
它对 ELF 文件大小贡献 = 0
它对 RAM 占用贡献     = 1536 B
```

### 为什么 `size` 把它算进 `bss`

`arm-none-eabi-size` 的 `bss` 列统计的是：

```text
"分配在 RAM 中、但在文件里不占字节的段"
```

`._user_heap_stack` 完美符合：

```text
有 RAM 地址和大小   ✓
文件里没有对应字节   ✓
```

所以它被算进 `bss` 列——**尽管它的名字里根本没有 "bss"**。

### 完整算一遍

```text
._user_heap_stack 自己的大小
    ├─ ALIGN(8) 补齐      =  0 ~ 7   ← 取决于 _ebss 落在哪
    ├─ _Min_Heap_Size     = 512
    └─ _Min_Stack_Size    = 1024
                           ─────
                           ≈ 1540

size.bss 报告值
    = .bss               (28)
    + ._user_heap_stack  (≈1540)
    ≈ 1568
```

> [!warning] 补齐算在 `._user_heap_stack` 头上
> 段首那句 `. = ALIGN(8);` 让该段从对齐地址开始，
> 补齐的这 4 字节**被计入段自身大小**，不单独列。
>
> 所以 `._user_heap_stack` 的 size 是 **1540**，不是 1536：
> ```text
> 4 (对齐) + 512 (heap) + 1024 (stack) = 1540
> ```
>
> 而且这个补齐量**取决于 `_ebss` 实际落在哪**，不是固定的 4。
> 本页给的是**计算方法**，不是让你背数字。
> 你自己构建一次，用第 13 节第 ② 条的命令把真实数字填进去。

### `end` / `_end` 是干什么的

```c
void *malloc(size_t n)   →   newlib 的 _sbrk()  →  从 end 往上涨
```

裸机 P0 阶段**没有任何人调用 malloc**，所以这个"堆"其实一直没被用过。
它只是被**预留**出来，防止后面栈向下增长时把它踩了。

## 12. `/DISCARD/` 和 `.ARM.attributes`（第 178-186 行）

```ld
/DISCARD/ :
{
  libc.a ( * )
  libm.a ( * )
  libgcc.a ( * )
}

.ARM.attributes 0 : { *(.ARM.attributes) }
```

### `/DISCARD/` 丢掉的是什么

注意它丢的是 **`libc.a ( * )` 里的内容被 `--gc-sections` 筛掉之后剩下的调试/元数据段**，不是把整个 libc 扔掉。

如果它真的丢掉整个 libc，你的 `--specs=nano.specs` 就白配了。

### `.ARM.attributes`

ARM 架构属性记录（用的什么 CPU、什么 ABI、软/硬浮点）。

**不加载到目标内存**，只在文件里。你配的是 `-mfloat-abi=hard`，属性里会记下来，用来防止软硬浮点库混链。

### ② 那个 1568 到底怎么来的

```bash
arm-none-eabi-size build/experiments/001_gpio_output/exp001_gpio_output.elf
```

然后**自己算**：

```text
size.bss  =  .bss 段大小  +  ._user_heap_stack 段大小

```

> 这就是为什么本页第 11 节比第 10 节更重要：
> **光看 `.bss` 段永远算不出 1568，必须知道 `._user_heap_stack` 的存在。**

> 完整诊断流程见 [[10_基础知识体系/02_构建与链接/24_从症状到诊断_数字对不上时怎么办]]。

## 14. 与简化示例的差异对照

你在基础知识层看到的是**教学简化版**，和这份脚本有几处不一样。**不是你记错了**：

| 项目 | 教学简化版 | 你的真实脚本 |
|---|---|---|
| Flash 区域名 | `FLASH` | `ROM` |
| `.bss` 写法 | `.bss (NOLOAD)` | `.bss` （无 NOLOAD，靠"没有 AT>"表达） |
| 段数量 | 5 段左右 | 15+ 段 |
| heap/stack | 通常省略 | `._user_heap_stack` 显式预留 |
| `.rodata` | 和 `.text` 合并 | 独立一段 |
| `ENTRY()` | 强调 | 只有一行，作用有限 |

> [!note] 为什么要先看简化版再看真实版
> 简化版让你**看见结构**（谁放 Flash、谁放 RAM、边界符号从哪来）。
> 真实版让你**看见现实**（厂商生成的脚本为什么这么长、多出来的东西都是干嘛的）。
> 直接从真实版入门会被淹没；只看简化版则会对不上自己的构建数字。
