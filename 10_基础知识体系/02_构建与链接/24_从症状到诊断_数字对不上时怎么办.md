# 从症状到诊断：数字对不上时怎么办

> [!abstract] 本页解决什么
> [[01_P0_仓库与构建基线/07_最小 Executable 与 ELF 体检]] 告诉你 `size.bss = 1568` 但 `_ebss - _sbss = 28` **是对的、不必惊慌**。
> 但那页给的是**结论**。
>
> 本页给的是**过程**——遇到一个对不上的数字时，从哪里下手、按什么顺序查、什么时候能停下来。
> 这套流程以后在 `.map` 文件、栈溢出、Flash 超限、DMA 越界上会反复用到。

## 1. 先建立一个原则

> [!important] 数字对不上时，先怀疑"我在比较两个不同口径的量"，再怀疑"工具出错了"
> 初学者最常见的反应是"链接器是不是有 bug / 我是不是配错了"。
> 实际上 **99% 的情况是**：两个数字来自不同的统计范围，本来就**不该相等**。

所以第一步不是去改配置，是**搞清楚每个数字的定义**。

---

## 2. 症状

```text
arm-none-eabi-size exp001_gpio_output.elf

   text    data     bss     dec     hex
    820       0    1568    2388     954
```

同时：

```text
arm-none-eabi-nm -n exp001_gpio_output.elf | grep bss

20000000 B _sbss
2000001c B _ebss
```

```text
_ebss - _sbss = 0x2000001c - 0x20000000 = 0x1c = 28 B
```

**28 ≠ 1568**，差了 1540。

---

## 3. 诊断路径

### 第 1 步：`size` 的三个列到底各统计什么

这是最容易跳过、也最关键的一步。

```bash
arm-none-eabi-size --help
```

```text
text  → 只读的、需要放进 ROM 的：代码 + 常量
data  → 有初值的可写数据。**会被算两次**（ROM 里存初值，RAM 里占运行空间）
bss   → 无初值的可写数据：RAM 里占空间，**文件里没有对应字节**
```

> [!warning] `data` 算两次是 `size` 默认行为
> 用 `-A` 可以看逐段明细，用 `-B`/`-SysV` 可以换格式。
> 先记住：`size` 报的不是"段大小表"，是**三个类别的汇总口径**。

所以 `bss` 列的定义是：

```text
"所有分配在 RAM 中、且文件里不占字节的段" 的总和
```

**注意是"所有段"，不是"名叫 .bss 的那个段"。**

### 第 2 步：把 ELF 的段全部列出来

```bash
arm-none-eabi-size -A exp001_gpio_output.elf
```

`-A` 会**逐段**列出。输出类似：

```text
section                size      addr
.isr_vector             336   0x8000000
.text                   484   0x8000150
.rodata                   0   0x8000334
.ARM                     ...
.data                     0  0x20000000
.bss                     28  0x20000000
._user_heap_stack      1536  0x20000020
...
```

> [!success] 到这里答案已经出来了
> `._user_heap_stack` —— 1536 B。
>
> `28 + 1536 = 1564`，再加上对齐补齐，就是 `size` 报的 `bss` 列。

### 第 3 步：搞清 `._user_heap_stack` 是什么

回到链接脚本 `platform/stm32f446ze/linker/STM32F446ZE.ld`：

```ld
._user_heap_stack :
{
  . = ALIGN(8);
  PROVIDE ( end = . );
  PROVIDE ( _end = . );
  . = . + _Min_Heap_Size;      /* 0x200 = 512 */
  . = . + _Min_Stack_Size;     /* 0x400 = 1024 */
  . = ALIGN(8);
} >RAM
```

```text
512 + 1024 = 1536 B
```

对上了。

详细逐行解释见 [[10_基础知识体系/02_构建与链接/23_真实链接脚本逐段注解]] 第 11 节。

### 第 4 步：确认它为什么被算进 `bss` 列

```bash
arm-none-eabi-objdump -h exp001_gpio_output.elf | grep -A2 user_heap
```

看它的 type 和 size：

```text
它分配在 RAM           ✓
它的类型是 NOBITS      ✓（文件里没有对应字节）
```

两条都满足 `size` 的 `bss` 列定义，所以被计入——**尽管它的名字里没有 "bss"**。

### 第 5 步：交叉验证，注意对齐补齐**在段内**

```bash
arm-none-eabi-objdump -h exp001_gpio_output.elf
```

看这两段的 VMA 和 size：

```text
.bss                 0x20000000      0x1c
._user_heap_stack    0x20000020    0x604
                     └─ 起点       └─ 大小
```

```text
.bss 结束于          0x20000000 + 0x1c = 0x2000001c
._user_heap_stack 起点 0x20000020        ← 前进了 4 字节
```

> [!warning] 这 4 字节算在**谁的头上**
> 段首的 `. = ALIGN(8);` 会让 `._user_heap_stack` 从对齐后的地址开始，
> 这 4 字节的补齐**被计入 `._user_heap_stack` 自己的大小**，而不是单独一项。
>
> 所以 `._user_heap_stack` 的 size 是 **1540**，不是 1536：
>
> ```text
> 4 (对齐补齐) + 512 (heap) + 1024 (stack) = 1540 = 0x604
> ```
>
> 验证方法：把它打印出来的 size 减去 `_Min_Heap_Size + _Min_Stack_Size`，
> 差值就是补齐量（0 ~ 7 字节之间）。

---

## 4. 完整答案

```text
size.bss
  = .bss 段的大小                (28)     ← 就是 _ebss - _sbss
  + ._user_heap_stack 段的大小   (1540)   ← 含段内对齐补齐
  ────────────────────────────────────
                                  1568
```

而 `_ebss - _sbss` 只描述了**第一项**。

**两个数字都没错，它们描述的是不同范围。**

> [!caution] 这是"演示版"，不是"你的实测值"
> 上面这套加减法用的是原笔记里记录的那组数字，用来**演示方法**。
> 你自己构建一次，把 `-A` 输出的真实数字填进去。
> **如果对不上，不要以为方法错了**——很可能是：
> ```text
> - 多了/少了别的 NOBITS 段（比如 .ARM.exidx 若被放到 RAM）
> - 你的 _Min_Heap_Size / _Min_Stack_Size 和这里假设的不同
> - _ebss 后面还有别的段
> ```
> 那就回到第 3 步，把 `-A` 的完整输出逐段加减一遍。

> [!note] 那 07 页原来的说法要不要改
> 07 页说"还包括其他 NOBITS / RAM 占用 section，**例如 linker script 预留的 heap/stack 区域**"。
> 这个说法**是对的**。
> 本页做的只是把它从"一句话结论"变成"一条你能自己走完的路径"。

## 5. 把流程抽象出来

> [!tip] 可复用的诊断模板
> ```text
> ① 写下两个对不上的数字
> ② 分别查清每个数字的定义（--help / readelf / 文档）
> ③ 找"谁被算进了第一个、却没被算进第二个"
> ④ 用 -A 逐段列出来，做加减
> ⑤ 到源头（链接脚本 / 编译选项）确认那段为什么存在
> ⑥ 交叉验证：用另一种工具（objdump / readelf）再算一遍
> ⑦ 写下"两个口径各是什么"
> ```
>
> 第 ⑦ 步最重要。**诊断的产物不是"对了"，是"知道两个数字各指什么"**——这样下次遇到新数字直接能判断。

## 6. 同类问题的常见形态

这套流程能解决的**同类**问题：

### A. Flash 用量比预期多

```bash
arm-none-eabi-size -A firmware.elf | grep -v "  0  "
```

找那些**你以为不该有、却占了 Flash** 的段（`.ARM.exidx`、被 `KEEP` 住的段）。

### B. `.data` 看起来是 0，但 RAM 用量不为 0

```text
data = 0  → 没有"有初值的可写变量"
bss  ≠ 0  → 但有"无初值的可写变量"和预留区
```

两个列本来就描述**不同类别**，不是同一个总量的两个视图。

### C. `_estack` 对不上 RAM 顶端

```bash
arm-none-eabi-nm firmware.elf | grep _estack
```

对照 `MEMORY` 里 `ORIGIN(RAM) + LENGTH(RAM)`。
对不上就是**链接脚本的 MEMORY 写错了**（比如芯片实际 512K RAM，脚本写了 128K）。

### D. 栈溢出但 `size` 说 RAM 还够

因为 `size` 只统计**静态**占用。

```text
size 报的 RAM 用量 ≠ 运行时峰值 RAM 用量
```

`.bss` + `.data` + heap/stack 预留是**静态**的；
函数调用深度、递归、`malloc`、局部大数组是**动态**的，`size` 看不见。

> [!warning] 这是 `size` 最危险的误用
> "`size` 说 RAM 才用 2K，我这芯片 128K，随便用" —— 这种想法会直接导致栈溢出。
> 静态布局检查和运行时栈水位监控是**两件事**。

## 7. 下次遇到新数字时的检查清单

```text
[ ] 我查过这个数字的官方定义了吗？
[ ] 两个数字是同一口径吗？
[ ] 我用 -A 逐段列过了吗？
[ ] 有没有"名字里没有关键字、但符合条件"的段（如 ._user_heap_stack）？
[ ] 对齐补齐算进去了吗？
[ ] 我回到链接脚本源头确认了吗？
[ ] 我用第二种工具交叉验证了吗？
[ ] 我能不能用一句话说清"这两个数字各指什么"？
```

前七条做完，第八条自然能答。
