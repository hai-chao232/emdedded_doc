# 编译器到底做了什么？

## 一句话先说清

编译器理解 C/C++ 语义，并根据目标 CPU、ABI 和优化选项，把程序转换成目标架构的低级表示/汇编，同时生成后续汇编和链接所需信息。

---

## 1. 编译器不是只做“语法翻译”

它还要决定：

- 用哪些寄存器；
- 哪些变量根本不需要内存；
- 表达式怎么优化；
- 函数怎样遵守 ABI；
- 什么代码可以删除；
- 对 `volatile` 访问不能怎样优化；
- 生成 Thumb/Cortex-M4 指令。

---

## 2. CPU 参数为什么会改变输出？

例如：

```text
-mcpu=cortex-m4
-mthumb
-mfpu=fpv4-sp-d16
-mfloat-abi=...
```

这些告诉编译器：

> 目标机器支持什么。

如果目标参数不一致，不只是“性能问题”，还可能导致：

- 指令不被目标 CPU 支持；
- 调用约定不一致；
- 浮点 ABI 冲突。

---

## 3. 优化会让“源码结构”和机器码不一一对应

```c
int x = 1;
return x + 2;
```

编译器可能直接：

```text
return 3
```

于是 x 根本没有实际存储。

所以调试优化构建时会看到：

```text
变量 optimized out
单步行号跳跃
函数被 inline
```

这不是 linker 错，而是编译器优化结果。

---

## 4. `volatile` 为什么影响编译？

编译器通常可以做：

```text
重复读合并
无用写删除
值缓存到寄存器
```

但 `volatile` 告诉它相关访问是可观察行为。

## 5. 编译错误发生在哪？

例如：

```text
unknown type name
undeclared identifier
incompatible pointer type
```

通常属于编译阶段。

而：

```text
undefined reference to foo
```

往往已经走到链接阶段。

分清阶段，排错会快很多。

---

## 6. 编译器能决定最终绝对地址吗？

通常单个 `.c` 编译时不能决定最终地址。

它会留下 symbol/relocation，等 linker 完成。
