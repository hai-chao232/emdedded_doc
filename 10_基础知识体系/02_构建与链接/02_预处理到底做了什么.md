# 预处理到底做了什么？

## 一句话先说清

C 预处理发生在真正编译之前。它处理 `#include`、`#define`、`#if` 等，把很多“文本层面的条件和替换”展开成编译器真正要看的 C 输入。

---

## 1. `#include` 不是“运行时加载文件”

```c
#include "stm32f446xx.h"
```

不是程序跑起来以后去磁盘读文件。

它发生在构建时。

概念上：

```text
main.c
+
头文件内容
+
条件编译
↓
一个展开后的翻译单元
```

---

## 2. `#define STM32F446xx` 为什么重要？

ST 头文件内部会有：

```c
#if defined(STM32F446xx)
#include "stm32f446xx.h"
#endif
```

所以编译命令里的：

```text
-DSTM32F446xx
```

会影响预处理结果。

如果 MCU 宏错了，编译器看到的设备定义就可能错。

---

## 3. 宏是文本替换，但不只是“字符串替换”

例如：

```c
#define BIT(n) (1U << (n))
```

源码：

```c
x |= BIT(3);
```

预处理后大致变成：

```c
x |= (1U << (3));
```

编译器随后才分析表达式含义。

---

## 4. 条件编译

```c
#ifdef DEBUG
...
#endif
```

决定某段源码是否进入最终翻译单元。

因此“源码文件里写了某段代码”不等于：

> 编译器一定看到了它。

---

## 5. Include Guard

头文件常见：

```c
#ifndef SOME_H
#define SOME_H
...
#endif
```

防止同一头文件在一个翻译单元里被重复定义。

---

## 6. 怎样直接看预处理结果？

可以用 GCC 的：

```bash
arm-none-eabi-gcc -E ...
```

输出通常很大，但在排查：

```text
宏到底是什么值？
哪个头文件实际被包含？
条件编译走了哪一支？
```

时非常有用。

---

## 7. 常见误区

### `#include` 会把 `.c` 文件也自动编译

不是。通常 include 头文件声明；`.c` 是否构建由构建系统决定。

### 宏有类型

普通宏本身没有 C 类型系统意义，展开后才由编译器解析。
