> [!abstract] 本节目标
> 不再抽象谈 `.data/.bss`。用两个具体变量，把 **Compiler → Linker → Flash → RAM → Startup → main** 走一遍。

## 1. 实验变量

真正动手时可临时加入：

```c
#include <stdint.h>

volatile uint32_t counter = 10;
volatile uint32_t flag;

int main(void)
{
    for (;;) {
        (void)counter;
        (void)flag;
    }
}
```

这里：

```text
counter → 可写 + 非零初值
flag    → 可写 + 没显式初值
```

`volatile` 只是为了让这个最小例子更容易观察，不负责初始化 RAM。

## 2. 构建前先预测

### `counter`

```text
目标文件：通常进入 .data 类 input section
Flash：保存初始值 10
RAM：存在运行时可写副本
Startup：Flash → RAM copy
main：看到 10
```

### `flag`

```text
目标文件：通常进入 .bss 类 input section
Flash：不需要保存一份全零镜像
RAM：预留空间
Startup：清零
main：看到 0
```

先写预测，再运行工具；输出不同再解释。

## 3. 第一步：只看 `.o`

找到 `main.c.o` 后可运行：

```bash
arm-none-eabi-objdump -h main.c.o
arm-none-eabi-nm -n main.c.o
```

观察 `counter` 与 `flag` 分别属于什么 input section。

此时不要把 `.o` 中地址当成最终 MCU 地址，因为它仍是 relocatable object。

## 4. 第二步：链接后看 ELF

```bash
cmake --build build --target exp001_gpio_output -v
```

然后：

```bash
arm-none-eabi-objdump -h firmware.elf
arm-none-eabi-nm -n firmware.elf
```

重点：

```text
.data VMA / LMA
.bss VMA
counter / flag final symbol
_sidata / _sdata / _edata
_sbss / _ebss
```

## 5. 先用假设地址练计算

假设：

```text
counter VMA = 0x20000000
counter LMA = 0x08001000
flag VMA    = 0x20000004
```

烧录后应这样想：

```text
Flash
0x08001000 : 0A 00 00 00   ← counter 初始镜像（小端示意）

RAM
0x20000000 : 未知          ← 不能先假设为 10
0x20000004 : 未知          ← 不能先假设为 0
```

C 语言要求的初始状态，需要 Startup 真正建立。

## 6. Linker 怎样描述 `counter`？

概念：

```ld
.data :
{
    _sdata = .;
    *(.data*)
    _edata = .;
} >RAM AT>ROM

_sidata = LOADADDR(.data);
```

于是：

```text
_sidata → Flash source
_sdata  → RAM destination start
_edata  → RAM destination end
```

如果 `.data` 只有一个 `uint32_t`，理想情况下区间长度约 4 B，但实际还要考虑其他对象与对齐。

## 7. Linker 怎样描述 `flag`？

概念：

```ld
.bss :
{
    _sbss = .;
    *(.bss*)
    *(COMMON)
    _ebss = .;
} >RAM
```

它只需要 RAM 运行空间，不需要 `AT>ROM` 保存整片零。

## 8. Reset 后 `.data` copy

概念流程：

```text
src = _sidata
dst = _sdata

while (dst < _edata) {
    copy word
}
```

对假设例子：

```text
Flash[0x08001000] = 10
          ↓
RAM  [0x20000000] = 10
```

这一步完成后 `counter` 的运行时副本才具有正确初值。

## 9. `.bss` clear

Startup 对 `[_sbss, _ebss)` 写 0，于是 `flag` 在进入 `main()` 前得到 C 语言要求的零值。

如果省略这一步，某次 RAM 碰巧为 0 也不能证明正确，因为“保证”已经消失。

## 10. 和当前最小 ELF 对比

之前真实最小程序：

```text
_sdata = 0x20000000
_edata = 0x20000000
```

所以 `.data length = 0`。

加入：

```c
volatile uint32_t counter = 10;
```

重新构建后，最值得观察：

```text
data 是否从 0 变成非 0？
_sdata / _edata 是否拉开？
counter 是否位于 SRAM？
.data LMA 是否位于 Flash？
```

这就是把抽象知识变成真正实验。

## 11. 用 `nm` 找变量

```bash
arm-none-eabi-nm -n firmware.elf \
  | grep -E 'counter|flag|_sidata|_sdata|_edata|_sbss|_ebss'
```

自己画一张地址关系图，而不是只保存命令输出。

## 12. 用 `objdump -h` 对照 VMA / LMA

找到 `.data`，检查：

```text
VMA 在 0x200...
LMA 在 0x080...
```

如果 `.data size > 0`，却完全不符合 linker 设计，就回头检查构建和 `.ld`。

## 13. 直接看 `.data` 内容

```bash
arm-none-eabi-objdump -s -j .data firmware.elf
```

如果 `counter = 10`，小端表示中可能看到：

```text
0A 00 00 00
```

具体布局仍以真实 section 和其他变量为准。

## 14. Debugger 的最终验证

烧录后：

```text
reset
break main
continue
```

观察：

```text
counter = 10 ?
flag = 0 ?
PC 在 main ?
SP 在 SRAM 合理范围？
```

这一步把静态 ELF 证据提升成真实运行证据。

## 15. 更强：观察 copy 前后

熟悉 GDB 后可以断在 `Reset_Handler`，单步到 `.data` copy 前后：

```text
复制前 RAM[counter]
      ↓
执行 copy
      ↓
复制后 RAM[counter] = 10
```

同理观察 `.bss` clear。

这是理解 Startup 最直观的实验之一。

## 16. 故障注入

### 跳过 `.data` copy

预期：`counter` 不再**保证**为 10。

### 跳过 `.bss` clear

预期：`flag` 不再**保证**为 0。

### 破坏 `_sidata`

预期：Startup 从错误 Flash 地址复制数据，说明 Linker Script 与 Startup 通过 symbols 构成契约。

> 某一次实验“碰巧值仍正确”，不能推翻因果关系。要区分偶然状态和语言/启动契约提供的保证。

## 18. 最终因果链

```text
counter = 10
C source
→ .data input
→ final .data
→ Flash initial image
→ RAM VMA
→ Startup copy
→ main sees 10

flag
C source
→ .bss input
→ final .bss
→ RAM reserve
→ Startup clear
→ main sees 0
```
