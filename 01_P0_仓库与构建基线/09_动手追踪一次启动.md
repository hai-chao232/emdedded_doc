## 1. 实验对象

建议在最小工程中放两个全局变量：

```c
#include <stdint.h>

volatile uint32_t counter = 10;
volatile uint32_t flag;

int main(void)
{
    for (;;)
    {
    }
}
```

预测：

```text
counter
→ 已初始化静态对象
→ 运行时位于 RAM
→ 初值 10 必须先保存在 Flash 初始化镜像
→ Reset_Handler copy 后 RAM 中变成 10

flag
→ 未显式初始化静态对象
→ 位于 .bss
→ Reset_Handler clear 后 RAM 中应为 0
```

## 2. 第一步：先做静态预测

不要一上来开 Debugger。

先用：

```bash
arm-none-eabi-size firmware.elf
arm-none-eabi-objdump -h firmware.elf
arm-none-eabi-nm -n firmware.elf
arm-none-eabi-readelf -h -S -l -s firmware.elf
arm-none-eabi-objdump -d firmware.elf
```

记录：

```text
Reset_Handler 地址
main 地址
_estack
_sidata
_sdata
_edata
_sbss
_ebss
counter symbol
flag symbol
.isr_vector VMA/LMA/Size
.data VMA/LMA/Size
.bss VMA/Size
```

> [!important] 这一步的产物是“预测”，不是“答案”
> 把这张表填完再插调试器。后面每一步运行时观察都要回来和它对照——**没有预测的观察不构成证明。**

## 3. 第二步：直接读取向量表的前两个 word

在 ELF dump 或 Debugger memory view 中找到向量表起始处。

记录：

```text
vector[0] = ?
vector[1] = ?
```

然后**用数值对照**，而不是靠感觉：

```text
vector[0] == _estack ?          ← 两个都要写出具体十六进制值
vector[1] == Reset_Handler ?    ← 注意可能差 1（见下）
```

举例，如果上一步 `nm` 得到：

```text
_estack       = 0x20020000
Reset_Handler = 0x08000278
```

而 dump 出：

```text
vector[0] = 0x20020000    → 与 _estack 完全相等
vector[1] = 0x08000279    → 比 symbol 大 1
```

如果看到：

```text
Reset_Handler symbol = 0x08000278
vector[1]            = 0x08000279
```

不要先判断为错误。

## 4. 第三步：让 Debugger 在真正的 Reset_Handler 停下

不要只在 `main()` 打断点。

目标：

```text
Reset
  ↓
CPU 完成硬件复位取向量
  ↓
停在 Reset_Handler 开始附近
```

观察：

```text
MSP
PC
LR
xPSR
```

验证：

```text
MSP 是否与 vector[0] 对应（写出两个具体值比对）
PC 是否进入 Reset_Handler
```

注意 Debugger 的“reset / halt / restart”语义可能与真正断电上电不同。

跳转：
- [[10_基础知识体系/01_计算机与MCU基础/14_上电 Reset 与重新执行程序的区别]]

## 5. 第四步：在 `.data` copy 前观察 RAM

在复制循环开始前：

1. 查看 `counter` 的 RAM 地址。
2. 查看 `_sidata` 指向的 Flash 初始化镜像。
3. 比较两边原始内容。

期望逻辑：

```text
Flash[_sidata ...]
包含 counter 初值镜像
```

而 RAM 中的 `counter` 在 copy 前不要预设一定是什么值。

特别注意：

> Reset 不一定等于断电，RAM 可能残留旧值。

因此真正验证的是“复制动作导致目标 RAM 变成正确值”，不是“复制前 RAM 必须是随机垃圾”。

## 6. 第五步：单步跨过 `.data` copy

逐步执行或在 copy loop 前后设置断点。

验证：

```text
copy 前  counter(RAM) = 某状态
copy 后  counter(RAM) = 10
```

并确认复制源与目标范围：

```text
source: [_sidata, ...)
target: [_sdata, _edata)
```

### 更强的做法：主动破坏再恢复

如果 copy 前 `counter` 恰好已经是 10，这次观察其实**什么都没证明**——它可能只是 RAM 残留。

更硬的验证：

```text
1. 暂停在 copy 之前
2. 用 Debugger 手动把 counter 所在 RAM 改成别的值（例如 0xDEADBEEF）
3. 继续执行 copy
4. 观察它被恢复成 10
```

这样证明的就是“copy 动作真的写了 RAM”，而不是“RAM 碰巧是对的”。

## 7. 第六步：单步跨过 `.bss` clear

在清零前看：

```text
flag(RAM)
```

执行 clear loop 后确认：

```text
flag == 0
```

同样建议用主动破坏法：先把 `flag` 改成非零，再执行 clear，观察它变回 0。

更严格地说，验证整个：

```text
[_sbss, _ebss)
```

范围被写零。

## 8. 第七步：观察 SystemInit / runtime / main

根据当前工程真实 Reset_Handler：

```text
Reset_Handler
  ↓
SystemInit
  ↓
.data copy
  ↓
.bss clear
  ↓
__libc_init_array（依工程实现）
  ↓
main
```

不要按教材猜调用顺序；以当前反汇编/源码为准。

对每一个调用至少回答：

```text
它真的被调用了吗？
调用发生在 .data/.bss 初始化之前还是之后？
当前工程中的实现在哪里？
```

注意区分：

```text
__libc_init_array  → 可以被 bl 的 C 函数
.init_array        → 它遍历的函数指针表（数据，不是代码）
```

## 9. 第八步：到达 main 后再次检查变量

进入 `main()` 后确认：

```text
counter == 10
flag == 0
```

这时你获得的证据链不是：

```text
main 跑了，所以 startup 肯定正确
```

而是：

```text
ELF 静态布局正确
+
向量表前两项可解释
+
Reset 后 MSP/PC 可对应
+
.data copy 可观察（且能被主动破坏验证）
+
.bss clear 可观察（且能被主动破坏验证）
+
控制流进入 main
```

## 10. 建议记录表

| 观察项 | 静态预测 | 运行时观察 | 是否一致 |
|---|---|---|---|
| vector[0] | `_estack` = ? |  |  |
| vector[1] | `Reset_Handler` + Thumb 状态 |  |  |
| MSP after reset | `_estack` |  |  |
| PC after reset | Reset_Handler |  |  |
| counter before copy | 不强行假设 |  |  |
| counter after copy | 10 |  |  |
| flag before clear | 不强行假设 |  |  |
| flag after clear | 0 |  |  |
| PC at main | `main` |  |  |

## 11. 故障注入（可选但很有价值）

### A. 临时破坏 `.data` copy

预期：

```text
counter 可能不再等于 10
```

### B. 临时破坏 `.bss` clear

预期：

```text
flag 不再有可靠的 C 语义初值保证
```

### C. 临时改变 linker symbol / section 放置

观察：

```text
ELF 静态布局怎样变化
运行时怎样随之失败
```

做完后必须恢复代码。

## 12. 启动链毕业标准

完成实验后，不看笔记说明：

1. CPU 从 reset 到 main 的每一步。
2. 每一步由硬件、Linker、Startup、runtime 中的谁负责。
3. 每个结论用了哪一种证据证明。
4. 哪些只是 ELF 的静态事实，哪些是 Debugger 看到的运行时事实。
