## 1. 从 `main.c` 到 MCU 运行

```text
main.c
  ↓
CMake target
  ↓
Platform requirements
  ├── STM32F446xx
  ├── CMSIS / Device include
  ├── CPU flags
  ├── startup
  ├── system
  └── linker script
  ↓
ARM GNU compile / assemble
  ↓
多个 .o
  ↓
Linker + Linker Script
  ├── 安排 Flash / RAM 地址
  ├── 解析 symbol
  └── 形成最终 sections / vector table
  ↓
ELF
  ↓
烧录 Flash
  ↓
MCU Reset
  ├── vector[0] → MSP
  └── vector[1] → Reset_Handler
  ↓
Reset_Handler
  ↓
SystemInit
  ↓
copy .data Flash → RAM
  ↓
clear .bss
  ↓
__libc_init_array
  ↓
main()
```

## 2. 每一层分别负责什么？

| 层 | 核心职责 |
|---|---|
| 仓库架构 | 把资料、平台、实验、第三方代码分清 |
| CMake | 描述构建对象和依赖 |
| Toolchain | 生成 ARM Cortex-M 可执行机器码 |
| Platform | 统一目标 MCU 的公共构建事实 |
| Linker Script | 安排地址与 linker symbol |
| Startup | 建立进入 C 程序前的运行环境 |
| ELF | 保存最终静态链接结果 |
| Debugger / Hardware | 证明程序真的按预期运行 |

## 3. 一定要区分“配置意图”和“最终事实”

CMake 里写：

```text
使用某 linker script
```

只是配置意图。

最终还要看：

```text
链接命令中是否真的出现 -T...
ELF section 是否真的落在预期地址
```

同理，target 依赖 Platform 后，也应该在最终编译命令中看到 `STM32F446xx` 和 CPU 参数。

## 4. 一定要区分“构建产物”和“运行状态”

ELF 里有：

```text
_sdata / _edata / _sbss / _ebss
```

只能证明 Linker 建立了这些 symbol。

不能证明：

```text
RAM 已经完成 copy/clear
```

后者需要真实运行观察。

## 5. `int x = 10` 的完整旅程

```c
int x = 10;
```

```text
C source
→ compiler
→ input .data
→ linker
→ Flash 中保存初始值 10
+ RAM 中分配 x 的运行地址
→ startup copy
→ main()
→ x == 10
```

## 6. `int y;` 的完整旅程

```c
int y;
```

```text
C source
→ compiler
→ input .bss
→ linker 在 RAM 预留
→ startup clear
→ main()
→ y == 0
```

## 7. CPU 为什么能找到 Reset_Handler？

不是因为它地址最小，也不是因为 MCU 直接读取 ELF `ENTRY`。

而是：

```text
Reset
→ 读取向量表
→ vector[1]
→ Reset_Handler
```

因此 `.isr_vector` 的位置和内容是关键。

## 8. 为什么 CMake 也放进这条启动链？

CMake 自己不在 MCU 上运行，但如果它没有把 startup、system、linker script 和 CPU flags 正确送进构建，后面的启动链根本不会形成。

所以课程从“源码如何成为可运行固件”的角度把它们串在一起。

## 9. 当前已经有的 P0 证据

我们已经实际检查过：

```text
main / Reset_Handler
_sidata / _sdata / _edata
_sbss / _ebss / _estack
text / data / bss
```

这说明 P0 不是只读文件，而已经开始对最终 ELF 做实证。

## 10. 未来可补的更强验证

在调试链完整后可做：

```text
烧录
→ break Reset_Handler
→ reset
→ 观察 MSP/PC
→ 单步 copy/clear
→ break main
→ 观察全局变量
```

但这不意味着要重新打开 P0 仓库建设；可以随真实实验自然补证据。

## 11. 四个核心问题

### `main.c` 为什么不能独自成为固件？

还缺目标架构、复位入口、向量表、内存布局和运行时初始化。

### Linker Script 与 Startup 为什么必须配套？

Linker 定义 `_sidata/_sdata/_edata/_sbss/_ebss`，Startup 按这些 symbol 执行初始化；它们共享一份地址契约。

### 为什么 ELF 不能代替 Debugger？

ELF 是静态构建结果；Debugger 能看到真实 CPU 的 PC/SP/寄存器/RAM。

### 为什么以后外设实验还要懂 P0？

因为 HardFault、中断不进、DMA 数据错、全局变量异常等问题，不一定来自外设本身。

## 12. 闭卷复述模板

尝试不看笔记说：

> 我在 `main.c` 写代码。CMake 通过 target 关系把实验、Platform、startup、system 和 linker script 组合起来；ARM GNU 把 C 和汇编变成目标文件；Linker 根据 linker script 把 section 放进 STM32F446ZE 的 Flash/SRAM，解析 symbol 并生成 ELF。固件烧录后，Cortex-M 复位时先从向量表取得 MSP 和 Reset_Handler，然后 Startup 完成 SystemInit、`.data` 复制、`.bss` 清零和运行时初始化，最后进入 `main()`。
