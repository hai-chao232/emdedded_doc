## 1. 从 `main.c` 到 MCU 运行

```text
main.c
  ↓
CMake target
  ↓
Platform requirements
  ├── STM32F446xx
  ├── CMSIS / Device include
  ├── CPU flags
  ├── startup
  ├── system
  └── linker script
  ↓
ARM GNU compile / assemble
  ↓
多个 .o
  ↓
Linker + Linker Script
  ↓
最终 ELF
  ↓
选择可烧录内容
  ↓
写入 MCU Flash
  ↓
Reset
  ↓
Cortex-M 读取向量表
   ├─ vector[0] → MSP
   └─ vector[1] → Reset_Handler 入口
  ↓
执行 Reset_Handler
  ↓
SystemInit
  ↓
.data：Flash 初始化镜像 → RAM
  ↓
.bss：RAM 区域清零
  ↓
__libc_init_array（依工程实现）
  ↓
main()
  ↓
应用逻辑
```

## 2. 三个世界必须同时看

### 源码世界

```text
startup
linker script
main.c
SystemInit
```

### 静态产物世界

```text
ELF
section
segment
symbol
machine code
vector table bytes
```

### 运行时世界

```text
MSP
PC
RAM
breakpoint
single step
main()
```

真正掌握启动链，必须让三个世界互相对应。

同一个 `counter` 就是最好的例子：

```text
源码世界   → uint32_t counter = 10;
静态产物   → .data section，VMA 在 RAM，LMA 在 Flash
运行时世界 → MSP 建立后，copy loop 把 10 写进 RAM
```

## 3. 六个最关键接口

### Linker Script → Startup

```text
_estack
_sidata
_sdata
_edata
_sbss
_ebss
```

### Startup → Cortex-M

```text
.isr_vector
Reset_Handler
exception handlers
```

### Flash → RAM

```text
.data copy
```

### ELF → 烧录器

```text
loadable contents + addresses
```

### Cortex-M 硬件 → 软件

```text
MSP/PC 从向量表获得初值
```

### Startup → C 程序

```text
准备 C 运行环境
→ main()
```

## 5. 一个容易搞反的细节：控制流 ≠ 地址顺序

真实构建里：

```text
main          0x08000250
Reset_Handler 0x08000278
```

`main` 的地址**更小**，但它**后**执行。

```text
控制流决定执行顺序，不是 symbol 地址从小到大自动执行。
```

这一条是本页最值得记的反直觉点。
